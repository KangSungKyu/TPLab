## 특성화 안전망과 fixture 정리의 현행 교훈

- [현행] 특성화 테스트는 현재 코드에서 통과하는 것을 먼저 확인한다. 임시 단일 변이 적용 → 의도한 이유로 실패 확인 → 원복 → 재통과로 민감도를 증명하고 변이 코드는 커밋하지 않는다. 기존 이름 집합·통과 수를 유지하면서 신규 case만 증가하는지 확인하고 전체 회귀를 반복한다. fixture 정정 뒤에는 정정된 fixture 기준으로 변이를 다시 실행한다. 근거: [UI-A 정상본·변이·원복](https://github.com/KangSungKyu/TPLab/blob/af084e0d0027c4098fad08c336ccb0753e1c7862/doc/retrospectives/2026-10-14-07-uicontext-safetynet-a.md#L79), [Guard-A 정정 후 변이 재실행](https://github.com/KangSungKyu/TPLab/blob/af084e0d0027c4098fad08c336ccb0753e1c7862/doc/retrospectives/2026-10-14-09-guard-safetynet-a.md#L267).
- [현행] Input/EventSystem 전역 상태를 건드리는 fixture는 InputTestFixture 구성 객체로 격리한다. SetUp에서 Setup을 호출하고, TearDown은 비동기 정리를 마친 뒤 finally에서 TearDown으로 복원하고 마지막에 LogAssert.NoUnexpectedReceived를 수행한다. 근거: [Guard-A 구성 객체·Setup·finally 복원](https://github.com/KangSungKyu/TPLab/blob/af084e0d0027c4098fad08c336ccb0753e1c7862/doc/retrospectives/2026-10-14-09-guard-safetynet-a.md#L220).
- [현행] TearDown은 ShutdownAsync 등 공개 종료 경로의 비동기 정리 완료를 기다린 뒤 LogAssert.NoUnexpectedReceived()를 async 본문 밖 IEnumerator 마지막에서 호출한다. async 식 본문에서 동기 LogAssert를 실행하면 scope 생성 전에 호출되어 “No log scope is available”로 실패할 수 있다. 기존 실패 관찰·예외 처리·단언을 약화하지 않는다. 근거: [Guard-A 실패 원문·scope 원인·정정](https://github.com/KangSungKyu/TPLab/blob/af084e0d0027c4098fad08c336ccb0753e1c7862/doc/retrospectives/2026-10-14-09-guard-safetynet-a.md#L67), [6개 TearDown의 완료 대기 보강](https://github.com/KangSungKyu/TPLab/blob/af084e0d0027c4098fad08c336ccb0753e1c7862/doc/retrospectives/2026-10-15-05-test-teardown-hardening.md#L25).
