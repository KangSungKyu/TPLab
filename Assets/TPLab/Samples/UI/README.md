# UIContext project demo

This optional project demo exercises UIContext HUD replacement, popup ownership and modal input, virtual inventory, and existing Core scene transitions. It creates only new sample-owned assets, including its input actions, and borrows configured prefab/font/service sources at runtime.

**Imported/compiled and 19 owned assets authored on Unity 6000.3.18f1.** Play/Player and visual acceptance remain pending. Use only after UIContextSettings/UIContextInstaller and the optional UIInputSystemAdapter are installed and reviewed. Existing module tests do not validate this demo.

## Promotion and owned outputs

Runtime and Editor sources live under `Assets/TPLab/Samples/UI/Runtime` and `/Editor`, with separate asmdefs. Optional `TPLab.UISamples.OptionalInput` references Core.Input and Unity.InputSystem explicitly; base TPLab.UI gets no new Input dependency. No new package, manager, singleton, service locator, or framework is needed. The Single variant uses the existing Core SingletonSceneRoot type.

The one-shot Editor menu `TPLab/UI/Create Sample` refuses an existing planned file or meta, links/reparse-point ancestors, and Play/compile/import activity before writing. It creates exactly these **19 new sample-owned assets**, plus their Unity metas and the three owned folders:

- Prefabs: HudA, HudB, PopupA, PopupB, PopupC, Inventory, Cell, SceneHud (`Prefabs/*.prefab`).
- Settings: CommonUI, SceneUI, TransitionsSingle, TransitionsAdditive (`Settings/*.asset`).
- Input actions: `Settings/UIInput.inputactions`.
- Scenes: UIContextHub, UIContextMain, UIContextArea, UIContextNested, UIContextBootstrapSingle, UIContextBootstrapAdditive (`Scenes/*.unity`).

Every scene is saved with its exact path through SaveScene. Only the exact new assets use CreateAsset/SaveAssetIfDirty or SaveAsPrefabAsset; the new UIInput.inputactions is written as JSON and explicitly imported. Additive temporary authoring scenes are closed individually and the previously active scene is restored; existing scenes are neither saved nor closed. There is no SaveAssets, existing sample builder invocation, Build Settings or playModeStartScene assignment, existing input asset read/save, or Init/protected scene mutation. Failed authoring can leave a partial set of those new outputs: it deliberately does not delete them or overwrite them on retry; inspect those exact owned paths before authorized recovery.

The builder uses the installed Input System public DefaultInputActions API to create fresh `Settings/UIInput.inputactions`, with Player.Fire and the full UI map. It preflights that exact new path/meta before folder or asset creation, writes asset.ToJson(), imports/loads the new asset, and destroys only the temporary generated asset with DestroyImmediate in finally. It does not call the generated wrapper Dispose during Editor authoring because that uses delayed Destroy. InputManagerInstaller borrows the imported sample-owned asset and owns its runtime action clone. The built-in LegacyRuntime.ttf is read-only borrowed. Existing Input sample input assets/scenes/controllers/transition settings are not read, loaded or changed. All new transitions use new owned Hub/Main paths and existing Core Bootstrap/scene lifecycle/callback machinery.

## Manual installation before Play

Builder does **not** change the original Build Settings. The user must add these five scenes for the selected entry variant (or a separately authorized isolated fresh consumer must supply its own build list), in this order:

1. `Assets/TPLab/Samples/UI/Scenes/UIContextBootstrapAdditive.unity` **or** `UIContextBootstrapSingle.unity`.
2. `Assets/TPLab/Samples/UI/Scenes/UIContextHub.unity`.
3. `Assets/TPLab/Samples/UI/Scenes/UIContextMain.unity`.
4. `Assets/TPLab/Samples/UI/Scenes/UIContextArea.unity`.
5. `Assets/TPLab/Samples/UI/Scenes/UIContextNested.unity`.

Open only the chosen Bootstrap entry for Play. The sample assumes the already installed Input System/uGUI/UniTask/Core dependencies, and the project's supported Input System backend. All definitions use direct prefabs, so this walkthrough installs no ResourceManagerInstaller and requires no Addressables catalog initialization. Do not run both bootstrap variants together or edit existing root assets. Scene-first entry without the Bootstrap controller is outside this walkthrough.

## Ownership and actual calls

Common installer order is Input -> sample scope -> UI. Install only creates scopes/metadata/native references: it does not create display clones. Scope.Install supplies the next UI installer's runtime factory/hooks before UI.Install, then registers disjoint Player/UI maps and mapless modal/transition layers before any layer acquisition. This does not rely on Controller.Awake preceding Core BeforeSceneLoad root restoration. Input source configuration is already serialized by the builder; the controller never reconfigures an installed input owner. Bootstrap.ShowCover starts the first explicit display; scope Prepare binds the already installed UIContext before UI first-HUD Prepare. First cover can bind sooner, after all Install calls finished. Modal factory uses the existing adapter AcquireModalBlock; compatible mapless BlockLower registration is this caller's precondition.

Layers are independent: game priority 0 Overlay owns Player, ui priority 2000 Overlay owns UI, modal priority 100 and transition priority 1000 are mapless BlockLower. InputManagerInstaller's separate preparation BlockAll remains until a callback observes commonRoot.IsPrepared and explicitly calls CompletePreparation. Neither UI nor another modal can release the game, transition, preparation, or another generation's modal lease.

The common UIContext owns HUD replacement, A/B/C/child, inventory and transition-shield clones/wrappers. Inventory has its own batching Canvas/GraphicRaycaster with **overrideSorting=false**, inherits the common managed host plane, and is opened before A/B/C. Its owned wrapper participates in the same modal boundary; no unmanaged prefab Canvas or sibling reordering bypasses UIContext. Fixed borrowed Canvases have orders scene=0, managed=100, diagnostic commands=300, loading=400 and cover=500.

The diagnostic command toolbar is an explicit project harness outside managed displays so a user can address a middle/blocked handle for a demonstration. It is not a claim that an ineligible managed button receives input. Real view close buttons live in the clone, request approval and are removed via RegisterCleanup. View focus uses handle.SetFocus during preparation. Only this explicitly referenced EventSystem/module and references created from InputManager.Actions/UI are used; there is no EventSystem.current or source action subscription.

Single uses a persistent common root: Bootstrap/controller, Input owner, common UI, EventSystem, toolbar/loading/cover survive old-scene unload. Additive retains its nonpersistent Bootstrap scene/common owner. Every Hub/Main/Area/Nested has its own nonpersistent SceneOwnedRoot and UIContextInstaller, a borrowed Canvas and a passive scene HUD; callback reads only that supplied root. Core loads/activates it before ConfigureSceneAsync, so its installers already ran: the callback never reconfigures its owner, provider, hosts or settings after Install. It borrows the already installed Context, records its scene-instance handle, and writes only that owned HUD clone after Prepare. Direct prefab data removes the need for cross-scene Input/Resource late installation or a global service locator. Transition teardown ends that scene context and leaves common UI/input alive. These scene HUDs have no InputManager/EventSystem binding and no interactive controls; cross-context unified modal/focus behavior is not claimed.

Normal reverse release awaits UI.Shutdown (including adapter-owned shutdown and generation leases) before sample reference/lease cleanup, then Input drains. Sample teardown uses its own temporary BlockAll until input drains; fallback Uninstall is idempotent and independently attempts ReleaseScope and shutdown-block return, preserving both errors in an AggregateException after remaining cleanup completes. It removes only its precise project button listeners and destroys only sample-created InputActionReferences and never disposes borrowed InputManager, EventSystem, native module, settings, prefab or font assets.

## Walkthrough

- `hud-a` / `hud-b`: actual SelectHudAsync replacement. Both retain reusable clones owned by the common context; the first HUD is selected by installer Prepare.
- `abc`: opens A Modeless, B Modal, C Modeless in order. `close-b` forcibly closes the middle B; observe C state/eligibility, native selected target and the delayed gameplay recovery while held controls release. Actual held mouse/submit/cancel/gamepad checks remain manual gates.
- `child`: opens C as a logical child of Visible A. `close-child` leaves A; reopen child then `close-parent` ends A's subtree. `front-a` calls BringToFront on that subtree. `mode-b` changes Visible B between Modal and Modeless.
- Veto defaults true. `user-c` requests Button approval; `outside-c` invokes the explicit project OutsidePointer callback; native Cancel goes through adapter RequestCloseAsync. `veto` toggles approval; `force-c` uses unconditional CloseAsync. `outside-c` is a harness callback, not an automatic outside-pointer detector.
- Inventory starts at 1000. Buttons select 1000/10000/0 (exercise 1000 -> 0 -> 1000), scroll to the last row, change the viewport between 240/360, and replace prepared data then explicitly Refresh. Native scroll and passive viewport reconciliation handle movement/resize; there is no per-frame Refresh. Data strings are prepared once; bind/unbind records the exact index/generation. Status shows Count, active/inactive/owned, cumulative created/destroyed and visible range. This diagnostic sample allocates status strings and is **not** a performance benchmark.
- `area` adds owned Area under the current primary; `nested` adds owned Nested under Area. `remove-nested` removes only Nested; `remove-area` removes Area and its Nested subtree. These use existing Core AddDerived/RemoveDerived definitions, always Additive even in Single entry. Status counts live/retired scene contexts by actual Scene.handle and disposal, while the common HUD/inventory/input remains owned by Bootstrap. Repeated or out-of-order requests are rejected/failed by Core and observed by the command handler.
- Loading presentation/manual Continue default on. `loading` and `manual` toggle policy for the next operation; `replace` executes Core TryTransitionAsync(to-main/to-hub) with that variant's Single/Additive mode. Disabled loading uses Core cover-only flow; automatic continuation uses the existing default await-free policy.

During both loading cover cycles the same independent transition lease stays held. ShowCover opens/reuses a separate `transition-shield` Modal/Reuse definition borrowing PopupB's source; its own clone remains hidden behind project cover/loading UI, vetoes Cancel, and is brought above managed views after inventory opens. This prevents below-loading A/B/C from accepting Cancel. RevealLoadingPresentation hides only the visual cover. Core sequence is PrepareLoading -> RevealLoading -> load/configure/root Prepare/presentation -> WaitForProceed -> second ShowCover -> old-scene finalization -> ReleaseLoading -> final HideCover. HideCover while loadingActive hides only the visual cover; final HideCover closes shield, reveals, and releases only the independent transition lease. Adapter recovery retains its own outgoing modal lease until raw controls release and the next native frame. Failure/cancellation keeps cover/blocking until Core recovery/owner shutdown, rather than granting gameplay permission.

Manual Continue stores the exact operation ID, waits raw button/navigation release plus a later frame and an enabled native module/UI map, then enables the visible external Continue pointer button. Native keyboard/gamepad Submit uses a scoped EventTrigger entry on the owned shield root, focused with handle.SetFocus; this avoids the adapter repeatedly replacing an external selection. Both native Submit and visible pointer Continue complete the same operation-specific wait. The exact entry/listener are removed in finally and cancellation links transition + controller destruction + shield display lifetime + loading GameObject destruction. Loading progress/release cleanup tolerates its destroyed UI references. Progress is stage-local ratio, never an invented overall percentage. Callback errors propagate to Core; command failures are observed and displayed, and actual failures keep a visible cover message plus Console exception.
